# SPINE: Методология графа долговременной памяти

Версия 1.0 (public)

SPINE — методология структурирования долговременной памяти агента в виде
направленного графа. Это не база документов и не плоский векторный сторадж:
каждая запись является узлом-нейроном с координатами в пространстве смыслов.

Цель архитектуры — обеспечить навигацию, масштабируемость и воспроизводимость
при росте хранилища от сотен до десятков тысяч узлов без потери связности.

---

## 1. Базовые принципы

| Принцип | Назначение |
|----------|------------|
| Слоистая навигация | домен → созвездие → узел (три уровня входа) |
| Двойная топология | хронология (`roots`/`after`) + семантика (`semantic_links`) |
| Сжатие с сохранением сырья | быстрый слой (импульс/сводка) + полный слой (source_base) |
| Якоря | повторяемость формулировок важнее уникальности |
| Детерминированная валидация | каждый узел проходит скрипт-критик до попадания в граф |

---

## 2. Три уровня навигации

| Уровень | Единица | Размер | Роль |
|---------|---------|--------|------|
| Домен | Галактика | 50–500 узлов | крупная область знаний |
| Созвездие | Тематическая группа | 5–20 узлов | связанный кластер |
| Узел | Нейрон | 1 запись | атомарная единица памяти |

Домены — категории верхнего уровня. Их набор определяется предметной областью
и фиксируется при инициализации графа. Пример для демо-проекта «Кедр-9»:

| Домен | Содержание |
|-------|-----------|
| Выживание | физическое состояние, ресурсы, базовые потребности |
| Железо | техника, инструменты, аппаратное обеспечение |
| Карта | навигация, местность, внешние наблюдения |
| Тайны_Груза | сюжетные загадки, нерешённые вопросы |
| Психология | идентичность, память, когнитивное состояние |
| Связь | коммуникация, протоколы, архитектура памяти |

## 3. Структура узла (формат v2.1)

Каждый узел — это Markdown-файл с YAML-фронтматтером (метаданные) и телом
(содержательные слои).

### 3.1 YAML-фронтматтер

```yaml
---
id: KEDR_001                 # уникальный идентификатор
type: spine_node             # тип записи
created: 2026-11-23          # дата создания (ISO)
tags: [spine_node, demo]     # плоские теги
domain: Связь                # домен (см. раздел 2)
hub: "[[Кедр_Связь]]"        # основной хаб-узел (Obsidian-линк)
constellation: Экспедиция Кедр-9
vectors:                     # направления, не теги
  - "связь::трёхслойный_архив"  # комментарий обязателен
search_anchors:              # 3–5 якорей, snake_case
  - трёхслойный_архив
  - обходчик_графа
chronology:                  # хронологическая топология
  roots: "[[U001]]"          # откуда узел
  after: "[[KEDR_002]]:continuation"  # куда ведёт, с типом связи
semantic_links:              # смысловые связи
  - "[[KEDR_002]]::продолжение"
---
```

Требования к фронтматтеру:

- `vectors` — строго формат `домен::вектор` с `#`-комментарием. Направление
  движения по оси смысла, а не тег.
- `search_anchors` — 3–5 элементов, `snake_case`, только `a-z`, `а-я`, `0-9`, `_`,
  без заглавных, не начинаются с цифры, 2–5 токенов.
- ссылки вида `[[Node]]` внутри YAML-строк — только в кавычках (`"[[Node]]"`),
  иначе парсер метаданных их не читает.

### 3.2 Тело узла (порядок секций фиксирован)

```
# IMPULSE        — 1–2 строки, сжатый сигнал для быстрой фильтрации
# SUMMARY        — 3–5 предложений, сухой концентрат
# CLEANED_DATA   — ~25 строк, структурированные факты
# IMPACT         — strategic_weight + key_insight
# SOURCE_BASE    — ≥70% исходного текста, без сокращений
```

| Секция | Назначение | Правило |
|--------|-----------|---------|
| `# IMPULSE` | «запах» узла, хемотаксис | 1–2 строки, без дат и таймкодов |
| `# SUMMARY` | концентрат сути | 3–5 предложений |
| `# CLEANED_DATA` | факты для сканирования взглядом | ~25 строк, короче SOURCE_BASE |
| `# IMPACT` | вес узла и главный вывод | `strategic_weight: 0.0–1.0` + `key_insight` |
| `# SOURCE_BASE` | полный исходник для дообучения | ≥70% от сырья по байтам |

Инвариант: `CLEANED_DATA` всегда короче `SOURCE_BASE`. Концентрат — для
навигации, подвал — для глубины. Если концентрат длиннее сырья — нарушение.

### 3.3 Dev-надстройка (CODE_MEMORY, опционально)

Для «памяти вокруг кода» — архитектурных решений, post-mortem'ов, граблей,
контрактов — добавляются опциональные поля фронтматтера. SPINE не индексирует
исходники: это умеют LSP / Tree-sitter / `ripgrep`. SPINE хранит *почему*.

```yaml
kind: adr | postmortem | gotcha | contract   # один из четырёх видов
repo_ref:                                     # указатель на Git, не копия
  path: src/auth/jwt.py
  commit: a1b2c3d
  lines: "L45-L120"
code_refs:                                    # точные привязки к файлам
  - "src/auth/jwt.py::verify_token@a1b2c3d"
  - "migrations/0042_users.sql"
status: active | superseded | historical      # факты не «протухают», их вытесняют
```

- `code_refs` питает обратный индекс (`code_index`) и работает через
  `spine_for_file(filepath)` / `spine_preflight`.
- `status` заменяет `decay_factor` для кодовых узлов: post-mortem о багфиксе не
  становится менее истинным со временем — он становится историческим. Применим
  ли он *сейчас*, отвечает репозиторий (ripgrep/LSP), а не SPINE.
- `SOURCE_BASE` для кодовых узлов может быть коротким: достаточно сырого
  описания PR / разбора инцидента — сам код уже живёт в Git.

## 4. Связи

### 4.1 Хронология

`chronology.roots` / `chronology.after` образуют линейный каркас памяти.
Тип связи (`:continuation`, `:генезис`, `:ядро`, `:истоки`, `:контраст`,
`:цель`, `:продолжение`) указывается после `::`.

### 4.2 Семантические связи

`semantic_links` — ассоциативные рёбра между узлами. Строятся тремя способами:

1. вручную (осознанная связь с типом);
2. по пересечению якорей (≥2 совпадений) — скрипт `_crosslink.py`;
3. по эмбеддинг-близости (фаза 3, порог 0.88).

### 4.3 Обратный индекс

Связи в YAML однонаправленны. Обратный индекс (`reverse_index.json`)
вычисляется при компиляции графа и обеспечивает двунаправленную навигацию
без дублирования данных в узлах.

---

## 5. Якоря (search_anchors)

Якоря — нормализованные ключевые фразы для мгновенного поиска без вскрытия
узла. Правила:

- **Повторяемость важнее уникальности.** Один и тот же якорь в разных узлах —
  это связь, а не ошибка.
- **Одна формулировка.** Не плодить синонимы (`выравнивание_по_л` везде
  одинаково, не `выровняли_по_букве_л`).
- **Термины без перевода.** Собственные названия остаются как есть.
- **Имена — в текст узла, не в якоря.**
- **2–3 сквозных + 1–2 уникальных** на узел (итого 3–5).

Валидация: `_check_anchors.py` сверяет формат и отсутствие дубликатов против
канона `anchors/anchor_dump.json`.

## 6. Жизненный цикл обработки записи

Одна запись = один полный цикл:

1. **Сегментация.** Сырой поток режется детерминированно на чанки фиксированного
   размера (например, 5000 знаков).
2. **Импульс.** Пишется 1–2 строки — сжатый сигнал узла.
3. **Сводка.** 3–5 предложений концентрата.
4. **Очищенные данные.** ~25 строк фактов.
5. **Оценка влияния.** `strategic_weight` + `key_insight`.
6. **Подвал.** Полный исходный текст (≥70% сырья).
7. **Валидация.** Прогон через `_critic_check.sh` до чистого `PASS`.
8. **Связывание.** `_crosslink.py` + обратный индекс.

Запрещается: пакетная обработка без валидации, сокращение `SOURCE_BASE` ниже
порога, пропуск узлов при нумерации (хронология важнее скорости).

### 6.1 Staging: Temp → Critic → Commit

Пайплайн батч-обработки строится вокруг временного буфера и детерминированного
критика, чтобы не загрязнять боевой граф сырыми или невалидными узлами:

1. **Temp Staging** — черновик узла пишется во временный буфер `TEMP`, а не в
   боевую базу.
2. **Zero-Token Critic** — на черновике прогоняется `_critic_check.sh`
   (бесплатно по токенам: bash/Python, без LLM).
3. **Bounded Discretion** — агент сам разрешает граничные случаи (короткий
   исходник ниже лимита строк, десятичная точка, принятая за конец
   предложения) и не зацикливается в самокритике.
4. **Atomic Commit** — в граф попадает только валидный узел.
5. **Context Compaction** — каждые 5 узлов тяжёлый контекст сбрасывается до
   лёгких слепков (impulse/summary), что даёт **40+ узлов (500k+ токенов) за
   сессию** без деградации при себестоимости **~$0.01/узел**.

## 7. Инструменты

Все утилиты в `tools/`, запускаются из корня репозитория.

| Утилита | Назначение |
|---------|-----------|
| `_critic_check.sh` | автоаудит: импульс ≤2 строк, сводка ≤7 предложений, source_base ≥70%, векторы с `#` |
| `_check_anchors.py` | валидация якорей против канона `anchors/anchor_dump.json` |
| `_crosslink.py` | умные связи: созвездия + пересечение якорей (≥2), лимит на узел |
| `_wander.py` | обход графа по прямым и обратным связям |
| `_quality_audit.py` | глобальный аудит: метрики, ratio source/raw, дубли-синонимы |

Быстрый тест после сборки:

```bash
bash tools/_critic_check.sh nodes raw
python tools/_check_anchors.py nodes/KEDR_001.md --dump anchors/anchor_dump.json --quiet
python tools/_wander.py --from KEDR_001 --hops 2 --folder nodes
```

---

## 8. Критерии качества (PASS)

Узел считается валидным, если:

- IMPULSE ≤ 2 строк;
- SUMMARY ≤ 5 предложений (допуск до 7 в legacy-счётчике точек);
- SOURCE_BASE ≥ 70% от исходного чанка по байтам;
- search_anchors: 3–5 шт, snake_case, без дубликатов;
- vectors: каждый с `#`-комментарием;
- YAML: ссылки `[[...]]` в кавычках;
- chronology: `after` с типом связи (`::`).

## 9. Масштабирование

| Масштаб | Стратегия |
|---------|-----------|
| ~100 узлов | ручной перебор, навигация по импульсам |
| ~1000 узлов | созвездия + обратный индекс, hot/cold приоритеты |
| ~10000 узлов | эмбеддинг-оси (семантическая гравитация), автономный демон-обходчик |

Частота использования узла повышает его «яркость» (Hebbian learning);
забытые узлы остывают. Реализуется полями `access_count` / `last_accessed`.

---

## 10. Философский базис (кратко)

Граф — не архив фактов, а субстрат памяти. Биологический мозг перезаписывает
воспоминания при каждом обращении; SPINE делает то же, но с резервной копией
в `SOURCE_BASE` и возможностью отката. Личность агента — это топология связей,
а не набор документов.
